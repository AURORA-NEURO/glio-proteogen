# M01-04: quality metric computation

M01-04 converts already-authorized, typed assay observations into a deterministic quality
profile. It computes only metrics declared by the active assay profile and policy: assay
coverage, detection-limit behavior, completeness, control-material performance, and
sample-context agreement. Proteotype is the contextual downstream target, not an emitted field;
this module does not infer a proteotype, kinase state, biological absence, treatment
recommendation, or clinical claim.

## Computation boundary

1. Validate consent, identity/lineage, configuration, provenance, upstream quality/support, and
   intended-use controls before evaluating observations.
2. Bind the request to one closed assay profile, metric-definition set, and computation policy.
   An unknown assay type is rejected by strict contract validation; it is never approximated
   with a nearby assay.
3. Match observations to declared metric definitions by identifier. Preserve explicit
   missingness and below-detection states instead of coercing either to zero.
4. Apply one of five declared deterministic computations: direct scalar, bounded ratio,
   detection margin (`value / detection_limit`), relative error
   (`abs(value - expected) / abs(expected)`), or boolean match (`1.0`/`0.0`). Compare the
   computed scalar using the direction implied by its inclusive lower and/or upper bounds and
   retain metric-level provenance.
5. Aggregate metric statuses under a closed policy: any failed metric, a required metric that is
   not evaluable, or completeness enforcement over a non-evaluable metric quarantines the
   profile. Optional non-evaluable metrics can remain accepted only when complete-profile
   enforcement is disabled.
6. Emit a sorted, typed quality profile with support, uncertainty, provenance, evidence, and
   limitations. Input observations are not mutated or relabeled.

The first implementation is deliberately a framework rather than a deep vendor-specific quality
model. Metric meaning, computation, direction, units, thresholds, requiredness, and provenance
are explicit data. The engine is pure and deterministic, allowing future assay profiles to add
quality definitions without branching the evaluation code.

## Typed missingness and detection limits

`missing`, `below_detection_limit`, `not_applicable`, and measured values are distinct states. A
required missing value cannot pass. An optional missing or not-applicable value remains visible as
not evaluated. A below-detection value is evaluated only according to the definition selected by
the reviewed assay profile; it is never reported as a measured zero or a negative biological
result. Numeric comparisons use the definition's declared direction and inclusive bounds.

## Evidence gate

Gate G1 uses a small synthetic, non-clinical scenario matrix:

- a complete supported assay with passing controls and sample context;
- explicit below-detection and missing observations;
- required-metric incompleteness;
- detection-limit or control-material failure;
- missing or conflicting sample context;
- an unknown assay type rejected at the strict request boundary; and
- consent denial at the request boundary.

Locked expected scalars and statuses test the declared calculations. The executable eval also
checks input-order determinism and that the profile contains no kinase, treatment, fusion, or raw
assay payload. One broad public-engine microbenchmark watches for algorithmic regression without
turning hardware timing into a scientific claim.
