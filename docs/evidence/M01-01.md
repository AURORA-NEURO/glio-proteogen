## Risk controls

- One strict JSON decoder rejects duplicate object keys and non-finite numbers consistently
  at fixture, plugin, CLI, and API boundaries; frozen contracts prevent silent coercion,
  unknown properties, and upstream mutation. User-facing validation diagnostics report
  locations and stable error types without echoing submitted values.
- The regex scanner rejects variable-length repetition—including adjacent optionals—before
  compilation; semantic-version strings, scalars, collections, issues, request bodies, and
  stored payloads have executable ceilings that bound resource use.
- Typed generic-control decisions must be accepted, lineage must be resolved, and consent must
  be granted before request hashing or persistence. Canonical identity-key binding detects
  lineage/document mismatch as a critical quarantine finding.
- Explicit unresolved states and quarantine-first precedence prevent missing or unsupported
  evidence from becoming a negative finding.
- Content-addressed, append-only events make request replay deterministic and detect event or
  projection tampering relative to a head trusted in memory or retained independently of the
  database. Outputs and stored payloads retain exactly seven privacy-minimized control-decision
  records; evaluation events retain digests and findings, not raw document identifiers or
  metadata values.

## Recovery and rollback protocol

1. Stop writes and capture the independently trusted event-head digest.
2. Run full chain verification. Do not bless a database whose event prefix does not match the
   trusted head.
3. Rebuild only derived protocol/checkpoint projections from the verified immutable event
   chain, then verify the rebuilt state before reopening writes.
4. Roll application code back to a previously reviewed version that understands the stored
   contract version. Never delete or rewrite source events as a rollback mechanism.
5. Preserve the failed database and verification output as evidence.

Automated recovery tests exercise valid projection rebuild, wrong-head refusal, tampered-event
refusal, and post-recovery verification. Operational release approval still requires the
external reviewer fields below.

The `release-candidate-evidence` workflow builds distributions twice, replays the exact wheel in
a clean locked runtime environment, emits a reproducible runtime SBOM rooted at that wheel, keeps
development-environment and runtime-dependency vulnerability audits as separate reports, and
attests candidate artifacts only after those checks pass. Automation never emits qualified
evidence. Qualification requires a protected external review that records every field below; a
tag, artifact upload, SBOM, provenance attestation, or successful workflow run is not approval.

The recovery head must be independently retained outside the SQLite database and governed as a
trust record. A fresh process using only a fully recomputed database has no basis for detecting
that rewrite. Host ACLs, safe SQLite snapshots, external-head retention, and reviewer approval are
deployment/governance responsibilities rather than properties supplied by the digest chain.
