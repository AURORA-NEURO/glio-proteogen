## Safety and replay assertions

- Seven execution controls, identity, lineage, provenance, consent, quality, support, and intended
  use are checked before upstream traversal.
- The request identity is bound to the execution-context identity before those controls or any
  upstream security metadata are traversed; mismatched context/request IDs abstain fail closed.
- Unknown fields, duplicate controls/findings/artifacts, hostile tokens, stale digests, malformed
  security posture, and output overwrites fail closed with sanitized boundary errors.
- FastAPI request and replay bodies are drained under the 4 MiB request / 8 MiB result ceilings;
  service mapping inputs enforce the same limits before model validation.
- Results expose seven `not_estimable` uncertainty dimensions, bounded evidence, provenance,
  limitations, review metadata, and the provisional ABI marker.
- Unsupported M27-05 media types and missing consent abstain without creating an access decision.
- A denied control or caller-declared threat yields a critical posture and an auditable deny event;
  this is access-policy evaluation only, not biological classification.
- Denial markers are read only from the explicit `action` policy field; opaque principal/resource
  labels such as `denylisted` or `threat-model` cannot turn an otherwise neutral action into a
  critical denial.
- Evaluated access and audit records bind the exact request principal, resource, action, policy,
  timestamp, and decision state before replay or result-digest verification.
- Provenance binds the request digest-derived activity, actor, module/version, exact upstream and
  source/consent input digests, consent decision, and all seven control decisions before replay or
  result-digest verification; rehashed provenance mutations are rejected.
